The system at one glance

KyleOS is a single-machine x86-64 operating system. Kernel services live in one higher-half address space. Each userspace process has its own virtual-memory map and reaches the kernel through a compact syscall ABI. The graphical desktop is deliberately outside the kernel: one shared userspace compositor owns display and input, while separate shell processes provide the desktop-environment personality.

Architecture1 shared compositor

Win95 and Aqua are desktop-shell processes and style profiles around the same kuid compositor. They are separate launch environments, not a live theme toggle.

Isolation1 map / process

User processes get private page tables, stacks, heaps, file tables, current directories, FPU state, and lifecycle state.

PersistenceFAT32 + RAMFS

The root disk persists changes. /dev, /tmp, and /proc are RAM-backed mounts recreated each boot.

Boot and initialization

The boot assembly establishes the architectural invariants that every later subsystem assumes. Initialization then proceeds in dependency order, ending by replacing the initial kernel task with the first userspace executable.

1 · MultibootThe loader receives a Multiboot boot-info structure and requests a 1280×720, 32-bpp framebuffer.
2 · Long modeTemporary 2 MiB mappings cover identity and higher-half addresses; PAE, EFER.LME, and paging are enabled.
3 · Core tableskmain validates the magic and discovers memory. GDT, TSS, IDT, paging, PMM, heap, and a protected kernel stack follow.
4 · Devices + servicesFramebuffer, PIC, mouse, ATA, PIT, exec, scheduler, FPU, RAMFS mounts, and MTRR reporting initialize.
5 · UserspaceThe idle task is created. The kernel tries /sbin/init, then shell fallbacks; PID 1 supervises the interactive shell.

Link and address layout

  • Linker entry: kernel_bootstrap.
  • Physical load begins at 0x00100000.
  • Higher-half kernel base: 0xffffffff80000000.
  • Direct physical map base: 0xffff888000000000.
  • The loader enters in 32-bit mode, constructs bootstrap tables, then jumps through a 64-bit GDT into Realm64 and finally the higher-half kmain.

PID 1 contract

/sbin/init is a small userspace supervisor. It starts /bin/nushell, waits for it, and restarts it if it exits. Kernel process management reserves PID 0 for idle and PID 1 for init; orphaned processes are reparented so they remain reapable.

Fallbacks in the kernel allow development images without a fully installed init to enter /bin/nushell or a root-level nushell.

Kernel subsystem map

The kernel is monolithic: its scheduler, memory managers, VFS, filesystems, drivers, interrupt handlers, and syscall dispatcher link into one image. The module boundaries below are source and ownership boundaries, not protection boundaries.

init

Entry, tables, syscalls

Bootstrap orchestration, GDT/TSS/IDT installation, exception gates, the shell fallback, ELF handoff, and the 34-entry syscall table.

sched

Tasks and execution

Task table, context switching, timer preemption, wait channels, process lifecycle, fork, ELF exec, argument setup, and status reporting.

mm

Memory

Early paging, physical-page allocation, protected higher-half mappings, per-process VMM sections, lazy file/anonymous faults, copy-on-write, and kernel heap allocation.

fs

VFS and filesystems

Path lookup, mount dispatch, descriptors, reference-counted open files, FAT32 persistence, RAMFS devices/pseudo-files, and anonymous pipes.

block

Storage

PIO ATA probing and transfer, MBR partition discovery, and a 512-sector read cache. The first partition is handed to FAT.

output

Human I/O

Framebuffer drawing/presentation, VGA and UART output, keyboard input, PS/2 mouse IRQ decoding and event queue, and unified output/input entry points.

irq

Interrupt control

PIC remapping/masking, interrupt acknowledgement, IDT stubs, kernel exception policy, and user-fault containment.

timer

Clocking

PIT at 100 Hz drives jiffies and scheduler entry. RTC supplies calendar time; millisecond timers convert onto the tick clock.

locks

Synchronization

Spinlocks protect short kernel critical sections. Mutex/sleep-channel paths allow tasks to block and wake without busy-waiting at the process level.

Processes, scheduling, and execution

Scheduling is preemptive round-robin on a single CPU. A timer interrupt enters the scheduler every 10 ms. Blocking kernel operations sleep on channels and wake when their condition changes, which is especially important for GUI pipes and child-process control.

Task record

Each task tracks PID and parent, exit status, name, process type, state, saved registers, kernel and userspace stacks, heap position, virtual-memory map, start address, context-switch count, working directory, 64 descriptor slots, a 512-byte x87/SSE save area, timer state, and a wait channel.

States are NEW, READY, RUNNING, BLOCKED, and DONE. The table supports up to 1,024 task records. PID 0 is the idle task and is skipped whenever ordinary runnable work exists.

100 Hz

PIT tick and scheduler cadence. FPU state and active page tables change with the selected task.

fork

Creates a child task with copied process state and a distinct descriptor table whose open-file objects are reference-counted. Writable userspace pages are shared copy-on-write until either process writes. The child returns zero; the parent receives the child PID.

exec

Serializes image replacement, validates the ELF header and program headers, reserves file-backed load segments, checks userspace addresses and permissions, builds the initial stack/arguments, then atomically adopts the new VMM map. Segment bytes arrive lazily on page fault.

wait and exit

A parent can block until a child becomes DONE, collect its status, and release the task slot. Exiting closes inherited descriptors, records status, wakes waiters, and schedules another task. User memory faults use status 139.

Blocking I/O

Pipe readers sleep while empty but writers exist; writers sleep while full but readers exist. Close and data transitions wake the opposing wait channel. This prevents the compositor, shell, IDE build tasks, and parallel demos from burning scheduler time while waiting.

Memory architecture

Physical

PMM

Boot memory-map data seeds physical-page ownership. The allocator supplies 4 KiB frames to page tables, user mappings, stacks, heaps, and kernel subsystems.

Kernel virtual

Paging + heap

The kernel occupies the higher half and has a direct physical map. Protected mappings replace temporary bootstrap tables. The kernel heap uses a first-fit allocator with splitting and coalescing.

Process virtual

VMM

VMM regions distinguish stack, text, and data; anonymous and file-backed storage; writable and executable policy. Each process starts with a 1 MiB stack near 0x700000000 and an initial heap near 0x600000000.

Page-fault decision path

  1. If a present userspace page is written, attempt copy-on-write resolution.
  2. If a page is absent but belongs to a valid VMM region, allocate it lazily. File mappings read only the overlapping bytes and zero the remainder.
  3. A kernel-mode fault may still be recoverable when the kernel is touching a valid lazy userspace buffer during a syscall.
  4. An invalid userspace fault prints a diagnostic, exits the task with 139, and schedules away.
  5. An invalid kernel fault is fatal and panics.

Why lazy mapping matters

ELF load segments do not have to be copied eagerly at exec. Pages are populated on demand from the executable, lowering launch work and memory use. Copy-on-write similarly makes fork cheap until the parent or child mutates shared data.

The tradeoff is more page-fault complexity: VFS-backed faults, COW ownership, address validation, and kernel/user fault context must agree.

Storage, VFS, devices, and pipes

All regular application I/O is descriptor-based. VFS resolves a path to a mounted device and filesystem operation, while each task’s descriptor points to a reference-counted open-file object carrying position and flags.

ATA and FAT path

The ATA driver probes legacy ports, validates the MBR signature 0xaa55, and exposes the first partition’s start, size, and type to FAT. Transfers use PIO LBA28 with a 512-sector read cache. Long device polls periodically yield so a slow disk does not completely monopolize the CPU.

FAT is the persistent root. Its mutation path is intentionally conservative and 8.3-safe for create, remove, rename, truncate, metadata, and regular writes.

Pipe semantics in the GUI

Each managed GUI application and the desktop shell use a pair of anonymous pipes with kuid. The same primitive supports IDE build output and the parallel-writer demo. Kernel-level blocking and readiness status let the compositor multiplex work while bounded application response deadlines prevent one client from freezing the whole desktop.

Shared compositor and desktop environments

The GUI follows the same separation of mechanism and policy used by X/Wayland-style systems, at a deliberately smaller scale. kuid is the mechanism: display ownership, input routing, window state, composition, and client supervision. A shell is policy and appearance: panel or dock, menus, launchers, task switching, and style metrics.

Managed application transaction

  1. kuid sends an event with serial, content-local pointer coordinates, current style, window size, argument, and typed path/text clipboard state.
  2. The client validates protocol magic/version, applies the supplied style, updates application state, and records drawing commands.
  3. The client returns a title, size constraints, timer request, action, display bytes, and optionally a damage rectangle.
  4. The compositor validates the response and replays the commands into that window’s cached pixel surface.
  5. Only the affected desktop area is recomposed and presented. Moving or exposing an unchanged window reuses the cache without asking the app to redraw.

Display vocabulary

The retained command stream supports filled rectangles, alpha-filled rectangles, lines, text, opaque bitmap rows, rectangular bitmap rows, and alpha bitmap rows. Text can be opaque or transparent and select the proportional UI or monospace font role.

Raster assets use the internal KIMG format; fonts use KFONT. Both shells and compositor cache decoded assets rather than reparsing them every frame.

Responsiveness comes from cached window surfaces, partial damage, sleepable pipes, stable shell-render caching, and response deadlines—not from putting GUI policy into the kernel.

Style contract

A kui_style carries style ID, flags, palette roles, selection/desktop/panel colors, and window metrics. Every app receives it, so widgets and content match the active shell without separate app binaries.

Aqua behavior

The dock caches image icons and grows the hovered icon from 58 to 76 px, with 66 px neighbors. It shows running indicators and minimized-window entries. Rounded window chrome is composited for every managed app.

Win95 behavior

The modular shell draws the taskbar, Start menu, running-window buttons, clock, and square classic chrome. It discovers the same application manifests and launches the same KUI clients.

Application and asset architecture

Applications are installed independently and discovered at runtime through /usr/share/applications/*.app. A manifest defines ID, label, executable, icon, optional argument and accepted type, launcher visibility, autostart/exclusive behavior, and initial geometry.

Asset pipeline

Source wallpaper and icon art lives under extras/desktop/art. Build rules use ImageMagick and repository converters to produce OS-native KIMG resources: desktop wallpaper, 64×64 app icons, and 16×16 Tetris block variants. Aqua receives its own blue wallpaper while Win95 retains the existing desktop art.

Font pipeline

Host DejaVu Sans, DejaVu Sans Condensed, and DejaVu Sans Mono sources are rasterized into KFONT assets. KUI chooses proportional antialiased UI text or fixed-width editor/terminal text by role. This keeps font rasterization out of the frame loop and makes both shells share the same legibility improvements.

System-call ABI

A user-callable IDT gate at vector 0x80 enters the assembly syscall bridge. The syscall number is in RAX; ordinary x86-64 C argument registers carry parameters. The dispatcher validates the table slot and returns a machine-word result.

Build, install, and disk-image pipeline

The repository produces two coupled artifacts: a freestanding kernel and a populated boot disk. Kernel and userspace have separate toolchain assumptions, then meet in the image staging pipeline.

Kernel objectsFreestanding x86-64 C/assembly across init, scheduling, memory, filesystem, block, IRQ, output, timers, and locks.
Kernel imageThe linker emits kernel.bin; objcopy also creates the Multiboot/QEMU-compatible 32-bit ELF container.
Static userspaceNewlib/libm plus repository extras and local program trees become staged binaries and converted GUI assets.
Manifest installimage/manifest.txt selects programs for /bin; PID 1 installs to /sbin/init; application manifests/assets install under /usr/share.
FAT32 diskA 256 MiB MBR image gets its first FAT32 partition, rootfs seed, programs, optional ports, Lua, and TinyCC content.

Compiler profile

Kernel code is freestanding, static, x86-64, and built for the higher-half large code model. GUI code uses optimization for rendering throughput; sensitive scheduler code is kept unoptimized where its assembly/context assumptions require it. Userspace links against the locally built KyleOS Newlib port.

Image lifecycle

The default disk is build/image/test-hd.img. A readiness marker allows normal rebuilds to reuse it, preserving user-created files and avoiding a costly repartition/reinstall cycle. Consequently, newly staged binaries do not appear in an already-ready image until the explicit reset/rebuild path runs.

Operational boundary: image-reset intentionally destroys the generated disk image. It is the correct way to force a fresh install, but not a harmless compile step.

QEMU runtime

The development target passes the kernel directly with -kernel and attaches the FAT32 hard disk. The boot framebuffer, ATA controller, keyboard, mouse, serial log, and CPU/MMU behavior form the hardware contract used by the current drivers.

Ports and optional payloads

Image rules can stage DoomGeneric, software Quake, Duke3D, Lua 5.4.4, TinyCC runtime/source, and game data. These are payloads above the stable kernel ABI; they do not become kernel modules.

Testing and the meaning of “complete”

The test architecture deliberately separates fast host-side logic checks from booted end-to-end behavior. The completion marker is a contract, not merely a string printed at the end of an optimistic script.

9

Booted test groups

Filesystem, copy, kernel log, wait, pipe, demand paging, expected user #GP containment, expected OOM containment, and 200-iteration exec stress.

1×

Completion marker

The harness requires exactly one ALL-TESTS-COMPLETE count=9. Zero markers, duplicates, explicit failure markers, early QEMU exit, and timeout all fail.

139

Expected containment

Fault and OOM tests pass only when the offending userspace task is killed with the expected status while the kernel and test shell remain alive.

Host unit and integration layer

  • Completion-control parsing validates that pass/fail markers cannot accidentally report success.
  • C token-highlighting, text selection/buffer editing, context menus, City simulation, Paint brush sizes, Tetris rules, and style helpers run without booting the OS.
  • A real Editor client is driven through KUI events to verify selection, Ctrl+C/X/V/A, right-click Delete, clipboard actions, and saved file contents.
  • KUI shell tests exercise protocol behavior, Win95/Aqua style selection, rounded Aqua windows, and dock magnification.
  • Tetris UI integration feeds real events, replays display commands, and proves the composed tile frame stays below the 256 KiB protocol cap.

Booted end-to-end layer

  1. Build kernel and userspace test payloads.
  2. Reset a dedicated test-suite image so stale binaries cannot masquerade as current results.
  3. Run host tests.
  4. Boot QEMU headless in snapshot mode and wait for Kyle OS has booted.
  5. Inject nushell < /tests/all.sh over the monitor/console channel.
  6. Parse the serial transcript and enforce the unique completion contract.

Interpretation: “all tests complete” means all nine in-guest groups returned their required status in a live kernel boot, the shell reached the final aggregator, and the external harness saw exactly one count-matching marker before timeout. It does not claim exhaustive GUI, hardware, filesystem-corruption, multiprocess-race, or long-duration stability coverage.
