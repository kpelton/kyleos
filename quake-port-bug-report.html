Doom & Quake port: the bugs behind the pixels

A technical postmortem of the kernel and Quake failures uncovered while bringing a 1996 game engine onto a small native x86-64 operating system. The visible failures looked like bad game data; most were really violations of CPU, ABI, or device contracts.

Platform: x86-64 KyleOS Renderer: software framebuffer Data: Doom WAD / Quake PAK Status: Doom + Quake installable together

The central lesson is that a successful game port tests much more than graphics. Quake stressed floating-point state, task switching, stack layout, storage polling, raw input, and a 32-bit virtual machine model. Doom and Quake now benefit from the same corrected OS foundation, though each should have exclusive framebuffer and keyboard ownership while running.

Detailed bug analysis

1. FPU/SSE state crossed task boundaries

9/10

Visible symptom

Quake aborted map loading with Bad surface extents, suggesting a corrupt BSP or renderer calculation.

Why it was deceptive

The map file and surface data were valid. Floating-point values changed only when a timer interrupt scheduled another process, so the corruption appeared inside unrelated geometry code.

Root cause

The scheduler restored an FPU context but did not first save the outgoing process’s live x87/SSE state. Registers therefore jumped backward or inherited another task’s values at each timeslice.

Correction

Save the outgoing user task with fxsave before selection and restore the selected task with fxrstor, including a valid architectural reset state for new tasks.

Relevant code: sched/sched.c, asm/asm_calls.s

2. Voluntary switches lost callee-saved registers

9/10

Visible symptom

At -O1, init repeatedly printed console exited; restarting and eventually the kernel faulted while writing through a null pointer in kstrcpy.

Why it was deceptive

The faulting string function was correct. Optimized ramfs_read_file held its user buffer in r13 across ksleepm(); unoptimized code happened to keep the same value on the stack.

Root cause

A voluntary context switch saved only RSP and RBP. The x86-64 ABI requires RBX and R12–R15 to survive a C call. Another task overwrote those registers before the original task resumed.

Correction

An assembly schedule wrapper now pushes every callee-saved general register onto the task’s own kernel stack. Restoring that stack naturally restores the registers before returning to C.

Relevant code: asm/asm_calls.s, sched/sched.c

3. QuakeC strings assumed a 32-bit address relationship

8/10

Visible symptom

Saving in Slipgate Complex printed done. and then segfaulted in GetEdictFieldValue. The saved mapname contained framebuffer-like bytes instead of e1m1.

Why it was deceptive

The crash happened after the save completed, and the immediate failure was a corrupted cache index. The original overwrite occurred earlier while formatting a string.

Root cause

QuakeC represents strings as signed 32-bit offsets from pr_strings. Native static strings such as sv.name could be more than 2 GiB from the Quake hunk on KyleOS. Subtracting the pointers truncated the offset and produced an unrelated address.

Correction

Copy native strings into hunk-owned memory with ED_NewString, initialize temporary QuakeC strings inside the persistent hunk, and bound diagnostic formatting with larger snprintf buffers.

4. Initial userspace stack violated the ABI

7/10

Visible symptom

Optimized user programs could fault on aligned stack operations, sometimes depending on whether the argument count was odd or even.

Why it was deceptive

Simple programs and debug builds worked. The failure appeared only when a compiler selected instructions or layouts that relied on the documented x86-64 stack contract.

Root cause

KyleOS enters newlib’s _start directly instead of arriving through a normal call. The constructed stack did not consistently reproduce the alignment a called function expects.

Correction

Pad the initial argument frame so RSP is 8 modulo 16 on entry; the startup push then produces a 16-byte-aligned frame.

Relevant code: sched/sched.c

5. The user stack was too small for Quake

5/10

Visible symptom

Pack-file and map-loading code could run beyond the original 128 KiB user-stack reservation.

Why it was deceptive

A stack failure during asset loading resembles bad file data, broken demand paging, or heap corruption. Quake also uses unusually large temporary stack frames in old loading code.

Root cause

The kernel reserved 32 pages for a user stack. Quake’s loader could consume slightly more than that in one path, leaving no safe growth margin.

Correction

Increase the reservation to 256 pages, or 1 MiB, while retaining demand paging so physical memory is committed only as touched.

Relevant code: sched/sched.h

6. ATA PIO readiness logic was incomplete

6/10

Visible symptom

Disk activity could hang, proceed before data was ready, or make filesystem and save operations appear unreliable.

Why it was deceptive

Failures surfaced above the driver as FAT errors, bad assets, or save corruption. QEMU timing can also hide polling mistakes that real hardware exposes.

Root cause

The old wait condition could stop once BUSY cleared even when DRQ was not asserted. It also lacked bounded timeouts and explicit checks for ATA error and device-fault status.

Correction

Add bounded wait_drq and wait_not_busy helpers, reject invalid status values and device errors, initialize the mutex before the first read, and iterate the port array by element count.

Relevant code: block/ata.c

7. Shell keys leaked into raw game input

3/10

Visible symptom

A game could receive stale key events typed while the shell still owned the console, producing unwanted motion or menu actions at startup.

Root cause

Switching into raw mode reset the byte-oriented raw queue but left make/break events in the keyboard event queue.

Correction

Reset both queue heads and tails at the ownership transition, along with the cooked line buffers.

Relevant code: output/input.c

Known issue: periodic console flicker

Open

Visible symptom

The text console periodically flashes over the game framebuffer.

Root cause

Quake and the VGA terminal share the same framebuffer. Quake’s diagnostic output reaches /dev/console; terminal scrolling performs a full redraw over the game, which the next game frame then replaces.

Recommended correction

Separate the serial/kernel log from the graphical terminal while a game owns the framebuffer, or add explicit framebuffer ownership so console rendering is suppressed and later restored. This issue was diagnosed but is not part of the completed fixes in this report.

Conclusion

The hardest work was not translating rendering code. It was making KyleOS honor the contracts that mature native software silently depends on: complete CPU state preservation, ABI-correct stacks and calls, bounded device protocols, sufficient virtual memory, and clear device ownership. Doom is the lighter workload; Quake acted as the deeper systems test and exposed faults that could affect any optimized program. Fixing those faults improved the operating system, not just one game.
