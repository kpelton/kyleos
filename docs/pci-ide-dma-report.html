PCI IDE bus-master DMA: what we built and what it taught us

KyleOS now discovers its IDE controller through PCI, enables PCI bus mastering, transfers disk sectors through a physical DMA bounce buffer, handles ATA IRQs, and safely falls back to PIO. The final debugging pass also exposed an important interaction between demand paging, interrupt gates, scheduling, and GUI deadlines.

Status: implemented, not yet committed Controller tested: QEMU PIIX3 IDE Mode tested: compatibility IRQ 14 DMA chunk: up to 64 sectors / 32 KiB

Outcome

Hardware discovery replaced assumptions

The ATA path selects PCI IDE channel resources and obtains the BMIDE base from BAR4. Compatibility ports remain as the standard PCI IDE compatibility-mode definition, not as the only controller discovery mechanism.

PIO is no longer the normal runtime path

After the filesystem is initialized, runtime reads and writes use READ DMA and WRITE DMA commands when the controller advertises bus-master support.

Disk waits no longer require long PIO loops

The disk controller copies data while the CPU is free. Fast completions are detected from BMIDE status; genuinely slow commands sleep and wake through IRQ 14 or 15.

Aqua is stable again

The kuid: shell frame render failed regression was reproduced, isolated to DMA behavior, fixed, and soaked beyond its previous consistent failure point.

Runtime data path

FAT or demand pager requests sectors
ATA mutex serializes the channel
PRDT points at the 32 KiB bounce buffer
BMIDE moves sectors without PIO copying
Data is copied to the caller and cached
PCI scan → IDE class 01:01 → BAR/channel setup → PCI command.bus-master = 1
         → program LBA task file → program PRDT → issue READ/WRITE DMA
         → brief BMIDE completion poll → IRQ sleep if still active → recovery/fallback

Safety and recovery policy

Boot remains conservative

MBR probing and initial FAT setup occur through PIO. DMA is enabled only after the disk and filesystem have been identified successfully.

Reads can safely retry

If a DMA read fails, the driver stops BMIDE, clears status, masks its IRQ, disables DMA, records the reason in klog, and retries with PIO.

Writes fail closed

A failed multi-sector DMA write is not automatically repeated because the device may already have committed a partial transfer. DMA is disabled and failure is returned to the caller.

Slow or missing hardware cannot hang forever

After a short status-poll window, a request sleeps for its IRQ with a two-second timeout. Timeout recovery stops the engine and clears device/controller state.

The Aqua failure: diagnosis and fix

  • Symptom Aqua exited to the serial shell with kuid: shell frame render failed even when Doom was never started.
  • Localization The message came from a failed render exchange between kuid and aqua-shell. The exchange has a 1.5-second inactivity deadline.
  • Control experiment The same disk image and launch sequence stayed alive under the pre-DMA kernel. That ruled out the Aqua protocol, assets, and image contents as the primary cause.
  • First hypothesis Small DMA operations were immediately sleeping, making each disk request pay for a scheduler round trip. A fast IRQ window helped normal system calls but did not solve the failure.
  • Key discovery Demand-page disk reads run inside the page-fault exception path. That interrupt gate enters with CPU interrupts masked, so the ATA IRQ cannot execute during a simple IRQ-only fast wait.
  • Final fix The driver briefly polls BMIDE's interrupt/completion status directly. It can therefore finish fast DMA during a page fault without enabling nested interrupts or performing a full task handoff. Slow commands still use the IRQ-driven sleep path.

What we learned

  1. DMA alone does not guarantee low latency. Per-command scheduling overhead can dominate a tiny hardware transfer, especially on a filesystem with one-sector clusters.
  2. Exception context matters. Code that works during an ordinary syscall may behave differently in a page-fault handler because the interrupt-enable flag is different.
  3. Hybrid completion is useful. Brief polling handles microsecond completions efficiently; IRQ sleep handles real latency without freezing the rest of the OS.
  4. A GUI error can originate far below the GUI. Aqua's protocol failure was the visible deadline miss, while storage and scheduling interaction was the actual cause.
  5. Baseline comparisons are essential. Repeating the test with the pre-DMA kernel separated a new driver regression from existing shell, wait-ABI, or application behavior.
  6. Read and write recovery should differ. Reads are repeatable; an interrupted write may be partially committed and must not be blindly replayed.
  7. Protocol deadlines are valuable diagnostics. Increasing Aqua's timeout could hide the symptom, but correcting I/O completion restored the expected timing.

Current boundaries and sensible next steps

Compatibility mode only for DMA

Native-mode task-file BARs are recognized, but native PCI interrupt routing is not yet represented by the legacy PIC setup. Those controllers currently use PIO.

Single active channel and one PRD

The implementation selects the channel containing the boot disk and uses one bounce buffer. Multiple disks, concurrent channels, and scatter/gather requests remain future work.

Measure on physical hardware

Record transfer latency, fast-poll hit rate, timeout count, and fallback count through klog. Use those measurements to tune the 4096-iteration completion window.

Advance the interrupt model

PCI interrupt-line routing, IOAPIC support, and eventually MSI-capable storage drivers would remove the remaining dependency on legacy IRQ 14/15 assumptions.
