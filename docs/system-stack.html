System block diagram

Important blocking boundary: KUI is a synchronous request/response protocol. While the desktop waits for one client response, that desktop event-loop iteration is blocked. Disk I/O is synchronous for the caller, but DMA waits sleep for IRQ completion and bounded ATA waits let other runnable processes execute.

KUI1 window protocol

Desktop → client

struct kui_event

  • Envelope: magic 0x3149554b (“KUI1”), version 9, monotonic per-window serial.
  • Geometry: content width/height and pointer x/y.
  • Pointer: changed button, current buttons, signed wheel delta.
  • Keyboard: key code, extended flag, pressed flag, modifiers, character.
  • Other: shell style, seed, 128-byte action argument, and 1 KiB clipboard state.
  • Types: INIT, POINTER, KEY, RESIZE, TIMER, REFRESH, CLOSE.
Client → desktop

struct kui_response + byte stream

  • Must echo magic, version, and event serial.
  • Flags select display, partial damage, title, size constraints, close, and timer updates.
  • Metadata: status, min/preferred size, timer period, title.
  • Shell actions cover path open, launch, save, clipboard copy, and settings changes with a 1 KiB argument.
  • display_bytes is bounded to 512 KiB and follows the response header.
Display command stream

Retained only for one response

Each command begins with type and size, followed by coordinates, foreground, background, and flags. Commands cover rectangles, lines, scaled text, bitmap rows, alpha drawing, partial bitmap regions, and indexed bitmaps.

The desktop validates and replays commands into a desktop-owned per-window pixel surface. Clients never receive a pointer to compositor memory.

Process launch contract

Two pipes + fork/exec

The desktop creates to_child and from_child, forks, maps the read side of the first to fd 0 and the write side of the second to fd 1 using dup2, then executes the app with --kui-client.

The desktop retains the opposite pipe ends, child PID, window geometry, cached pixels, serial, title, constraints, timer state, and z-order.

Storage and filesystem path

VFS boundary

Generic objects

  • vfs_device: mount and filesystem ops.
  • inode: identity, type, size, FAT directory location.
  • dnode: directory traversal result.
  • file: refcount, position, flags, optional pipe.
  • poll: pipe events wake sleepers; regular files are immediately ready.
FAT boundary

Root disk filesystem

  • MBR selects partition start and size.
  • Boot sector configures FAT geometry.
  • FAT table maps cluster chains.
  • fat_lock serializes mutation.
  • Cluster writes use multi-sector ATA batches.
ATA boundary

DMA/PIO LBA28 contract

  • 512-byte sectors; up to 255 sectors per command.
  • A 32 KiB, 64-KiB-boundary-safe bounce buffer backs one physical PRDT.
  • DMA completes from BMIDE status or IRQ 14/15 with a two-second timeout.
  • Failed reads fall back to bounded PIO; uncertain writes fail closed.
  • Read-through cache; writes invalidate affected entries.

Principal runtime flows

Launch and render one KUI window

1. LaunchDesktop creates two pipes, forks, remaps fd 0/1, and execs the app.
2. EventDesktop fills KUI1 INIT/INPUT/TIMER event and writes it to the child.
3. DrawClient records fill/line/text commands in a private command buffer.
4. RespondClient writes response header and bounded command bytes to stdout pipe.
5. CompositeDesktop replays into its window surface, then draws chrome, taskbar and cursor.
6. PresentDesktop invokes framebuffer syscall 23/32 to update hardware pixels.

Write a file to FAT

1. libc writeUserspace supplies fd, buffer and byte count through syscall 12.
2. FD lookupCurrent ktask resolves fd to a refcounted struct file and position.
3. VFS dispatchvfs_write_file selects the mounted filesystem's write_file operation.
4. FAT mappingBytes map to clusters; chain and directory metadata are maintained under fat_lock.
5. ATA batchwrite_sectors programs LBA/count, waits for DRQ once per sector, outputs words.
6. CommitOne CACHE FLUSH completes the batch; return values propagate to userspace.

Boot and initialization order

1. CPU tablesMultiboot entry, GDT, TSS, IDT, early physical memory discovery.
2. MemoryPMM, paging, heap/VMM, framebuffer mapping and kernel stack.
3. DevicesPIC and mouse initialize; ATA probes ports and mounts the FAT root.
4. RuntimeTimer, ELF exec subsystem, scheduler, FPU and RAMFS initialize.
5. PID 1Idle task is registered; /sbin/init loads from VFS, with shell fallbacks.
6. DesktopUserspace init/shell launches desktop; desktop loads app config and autostarts clients.

Memory, ownership, and concurrency boundaries

No GUI SHM

Current window transport copies commands

Application pixels are not shared with the desktop. A client owns a temporary command buffer; kernel pipes copy its serialized commands; the desktop owns a replayed pixel surface for each window and the final full-screen surface.

Scheduling

Processes remain isolated and independently schedulable

The PIT invokes the scheduler at 100 Hz. Mutex contention sleeps tasks on a wait channel. ATA's long status waits yield only after scheduling has started, keeping boot-time disk probing safe.

Poll-driven desktop IPC

Disconnect fan-out plus bounded replies

Each desktop iteration polls the shell and all visible application response pipes as one set, closing hung-up or invalid clients immediately. Event/reply exchanges remain serial, but their reads sleep in poll and retain a 500 ms protocol deadline.

Storage serialization

Correctness locks remain narrower than the scheduler

fat_lock protects FAT mutations and ata_mutex serializes the controller. They can block competing filesystem users, but do not disable timer interrupts or globally stop unrelated runnable tasks.
